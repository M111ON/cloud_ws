# REPORT 2026-09-29 — memcore เร็วขึ้น · chatchunker dedup · embed bench (ONNX vs GGUF)

## 1. memcore retrieval (repo: cloud_ws/memcore)

สายความเร็ว (10 คำถาม randomized หนึ่งประโยค/วัน เดือน ก.ย.):

| ระยะ | wall/query |
|---|---|
| เดิม — CLI fork python ต่อ query | เฉลี่ย 1,249ms (≈98.6% = startup+imports) |
| + ใน-process, ONNX local (ไม่ใช้ API) | ~170ms |
| + vector fetch cache (`PRAGMA data_version` guard) | **warm เฉลี่ย 55ms** (fetch 187→0 · embed 17 · dot 14 · ftstm25 2) |

บั๊กที่แกใน `v2.py` (ทั้งหมดเจอบนทาง verify MCP เทียบ CLI):
1. RRF unpack สลับ (rank, idx) → vector path ไม่เคยชนะ FTS (structural)
2. FTS ไม่มี `ORDER BY rank` → ได้ rowid order ไม่ใช่ความเกี่ยวข้อง
3. term join แบบ AND → คำไทย/mixed tokenized เป็น fragment → FTS ว่าง → junk top-1 (แก้เป็น OR fallback)
4. embedder ถูกสร้างใหม่ทุก query (~3.5s) → cache session เดียว

MCP (`memcore_mcp_server.py`): store **v2 เป็น default** (MEMCORE_STORE=v1|v2 สลับได้, แยกไฟล์/ embedding space ไม่ปน), โหลด `.env` เองเพราะ host บางตัวตัด env ทิ้ง

## 3. Embed bench: ONNX vs GGUF — โมเดลเดียวกัน (multilingual-e5-small, int8 เทียบ Q8_0)

| | ONNX int8 (memcore ปัจจุบัน) | GGUF Q8_0 + llama-server (build_zc2) |
|---|---|---|
| warm call | **~15ms** | best 47–280ms |
| รันยาว | นิ่ง ~15ms | erratics — stall 1.5–2.7s เป็นบางครั้ง (llama 0% CPU, ไม่ใช่ HTTP/Defender; cause unpinned) เฉลี่ย 0.8–1.7s |
| overhead | ไม่มี | +HTTP, โหลด 126MB, start 2.4s |

สรุป: **อยู่ ONNX ต่อไป** — ของ optimize ใน llama.cpp (gguf_box zero-copy) ช่วย big-model weight streaming ไม่ใช่ encoder สั้น ๆ 118M. ผลบันทึกเป็น memory #6399
陷阱 ตอนวัด: `run(str)` = encode ทีละตัวอักษร (ดูเหมือน 230ms ช้าผิดปกติ) ต้อง `run([str])` — กัน false-slow
